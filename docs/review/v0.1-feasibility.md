# v0.1 feasibility and completeness review

**Decision: feasible as an experimental, gate-first release; real-host enforcement remains conditional on Host Profile evidence.**

This review uses only `spec/OXRAIL_SPEC.md` as the product authority.

## What is feasible now

- A GitHub repository marketplace can package one Oxrail plugin with a Skill and Codex lifecycle hooks.
- Codex publicly supports non-managed plugin hooks, `PreToolUse`, `PostToolUse`, hook matchers, and explicit user trust of the current hook definition.
- A local doctor can verify installed artifacts, registered events, observed hook markers, profile shape, and capability status without issuing a browser action.
- A host-provided harmless synthetic probe can prove a route without user-task side effects.
- If no equivalent probe exists, the hook can passively mark the first naturally occurring browser call while returning the original native action/result unchanged.
- Hook failure can be neutral: native Computer Use continues while Oxrail reports `BYPASSED` and inactive protection.

## What remains host-dependent

- Whether the exact Chrome Computer Use route reaches public Codex hooks.
- Whether every browser primitive is visible separately or only through a transaction/script wrapper.
- Complete `PreToolUse`/`PostToolUse` coverage, bypasses, timing, and result-media fidelity.
- Secure same-tab Handoff, exclusive observation/action lease, non-secret completion detection, and automatic resume.
- Any ChatGPT Work or ChatGPT Web lifecycle-hook behavior; Codex evidence cannot establish it.

These are `PROBE_REQUIRED`, not implementation facts. Until evidence exists, the honest mode is `ADVISORY_ONLY`, `TRANSACTION_GUARD`, or `UNSUPPORTED` as derived by doctor; Safety/Handoff stay `INACTIVE`.

## Completeness against the v0.1 loop

The design is complete enough to implement and test because it defines:

- install source and plugin identity;
- manual Hook review/trust and reauthorization after hash changes;
- new-thread Skill loading;
- `INSTALLED → CONFIGURED → VERIFIED` setup states;
- the complete doctor checklist and harmless-probe preference;
- passive first-call behavior with no block/rewrite/replay;
- fail-open native behavior and explicit `BYPASSED`/`INACTIVE` UI;
- controlled fixtures, NIF regression criteria, evidence artifacts, and a release gate;
- forbidden claims when route, granularity, performance, or Handoff evidence is absent.

## Release blockers

v0.1 must not be presented as accepted until a real Guard runtime adapter exists and `WP-RLS-010` has reproducible evidence for marketplace validation, build/tests, setup state transitions, passive pass-through, fail-open behavior, and the applicable Native Interaction Fidelity checks. A local synthetic harness does not prove the real Chrome route; public copy must keep that distinction visible.
